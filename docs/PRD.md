> **一句话立意**：做一个开源的通用计算机辅助翻译（CAT）软件——它既是大多数翻译工作的**起点**（在这里开始翻），也是**终点**（在这里完成、审校、导出），更是所有翻译成果的**沉淀中枢**（TM / 术语 / 语料在这里汇聚，并由 AI 持续提炼为可复用资产）。**凡是需要翻译资产沉淀的地方，本项目都应该能优雅接入。**
>
> 本项目面向个人译者、小团队与内部自用场景，以开源方式建设。评价一个功能是否纳入的标准是：**它是否让"翻译 + 资产沉淀"做得更快、更准、更省心，或让本项目更容易被接入与扩展。** 当前范围不包含面向外部客户的运营能力（如报价计费、客户门户、供应商采购等），详见 §2.5。
>
> 行业与架构调研见附录 A（2026-07 检索）。本文档只回答"做什么、为谁做、做到什么程度"；技术设计（design.md）、执行计划（implement.md）另行撰写。

## 0. 产品边界

两类"不做"必须区分清楚：

1. **当前范围不包含**（面向外部客户的运营与重型企业管理能力）：客户门户、报价/费率/发票、供应商采购/外包、抽成市场、企业级数据隔离与重型合规、复杂权限审计。这些能力不服务当前目标用户，默认不进入需求评审。
2. **核心不内置、插件可扩展**（技术边界，靠生态承载）：软件本地化资源格式（`.po`/`.resx`/`.strings`/`.arb` 等）、VCS/CMS/设计工具连接器、持续本地化流水线。**核心保持精简**，但**插件系统与格式过滤器架构为其预留标准扩展点**——谁需要谁写插件，或社区共建。

一句话：**打开技术天花板，收紧当前产品范围。**

## 1. 背景与动机

### 1.1 现状的低效（需求出发点）

个人译者、小团队、小型企业内部有稳定、反复出现的翻译需求（文档为主）。当前处理方式的低效：

- 裸用 ChatGPT/DeepL 逐段贴：无记忆、术语不统一、版式全丢、重复劳动、**成果无处沉淀**；
- Word 对照手翻：慢、无复用、无质检；
- Trados/memoQ：贵、重、仅 Windows、为大 LSP 流程设计，个人自用是负担；
- 云平台（Smartcat/YiCAT）：纯云、按量订阅、面向商业协作。

**更深一层的痛点：翻译成果留不住。** 今天在 A 工具翻的东西，明天在 B 场景用不上；这次的术语决定，下次又从零开始。翻译资产（TM、术语、双语语料）在不同工具、不同场景之间**割裂、流失、无人养护**——这恰恰是 AI 时代最不该浪费的东西：干净的双语语料是喂养一切 MT/LLM 接地翻译的燃料。

### 1.2 为什么是"开源 + 通用 + 资产中枢"

- **开源**：翻译资产（尤其是长期积累的 TM/术语）是使用者的命根子，托付给一个可审计、可自托管、不会突然涨价或停服、数据格式开放的开源项目，比托付给任何商业黑箱都更安心。开源也让"凡需接入处皆可接入"成为现实——生态可以自由为它写过滤器、连接器、插件。
- **通用 CAT**：翻译不只发生在文档里。长期看，本项目应能承接文档、字幕、乃至（经插件）软件字符串等**任意可切分为"源—目标段落对"的翻译对象**，让它们的成果都回流到同一个资产中枢。文档翻译是**验证核心、打磨体验的起点**，不是能力的边界。
- **资产中枢**：把 TM/术语/语料从"编辑器的附属品"提升为**产品脊梁**。无论翻译在哪发生（本工具编辑器 / 外部导入 / API 接入 / 插件回流），成果都沉淀到这里，并由 **AI 持续养护**（去重、纠错、对齐、质量分级、术语挖掘）。这是本项目相对一切现有工具的核心差异。

### 1.3 从行业与开源生态里，我们取什么

（详见附录 A 对 Trados 2026、memoQ 12、Phrase、Okapi、Weblate、OmegaT 的调研）

**取（与本项目定位契合）：**
- **Okapi 式架构**：过滤器（格式→统一内部表示）+ 管线步骤（可链式组合的处理单元）——这是"核心精简、格式与处理靠插件"的黄金范式；
- **Phrase Automated Asset Curation 式 AI 养护**：规则过滤（长度比/去重/近似去重/非可译）+ ML 过滤（语义对齐检测错位对、语言识别）+ 质量分过滤——这是"AI 辅助资产沉淀"的直接武器库；
- **2026 CAT 的 7 项 AI 标配**：编辑器内 LLM 助手、接地预翻译、AI 术语提取、QE 质量预估、AI 语义 QA、RAG 上下文、代理式链路；
- **插件生态**：Trados AppStore（80+ 插件）、OmegaT 插件社区证明可扩展性是 CAT 长期生命力的来源；
- **Weblate 式接入**：REST API + webhook + 增量同步的"翻译成果流动"模型（不取其 VCS 绑定，取其"可被接入"的开放性）。

**不取（当前范围外）：**
- 客户门户、报价/发票、供应商管理、抽成市场、SLA、企业级隔离与重型合规、复杂权限审计。

### 1.4 隐私立场

数据默认在使用者本机、密钥 BYOK 自填、可自托管——这是开源桌面工具应有的务实默认。因此不做数据流审计面板、涉密模式、静态加密卖点、合规认证模块。想限制引擎范围的人可用"引擎白名单"这一朴素选项自取。

## 2. 产品定位

### 2.1 一句话定位

**一款开源、跨平台、AI 原生的通用 CAT 软件与翻译资产沉淀中枢——以文档翻译为起点，把 TM 复用、术语一致、版式保真、AI 全流程辅助与开放可扩展装进一个轻到能 30 分钟上手的工具，让任何需要翻译与资产沉淀的场景都能接入。**

### 2.2 三层产品身份

```
┌─────────────────────────────────────────────────────────┐
│  身份三：资产沉淀中枢（长期护城河 / 产品脊梁）             │
│  TM · 术语 · 双语/单语语料 + AI 持续养护 + 开放接入        │
│  凡翻译成果，皆回流于此                                    │
├─────────────────────────────────────────────────────────┤
│  身份二：通用 CAT 工作台（长期身份）                       │
│  任意"源—目标段落对"对象的翻译/审校/QA；格式靠过滤器插件   │
├─────────────────────────────────────────────────────────┤
│  身份一：文档翻译工具（起点 / MVP 首要场景）               │
│  Office/PDF/文本 高保真往返，AI 辅助，开箱即用             │
└─────────────────────────────────────────────────────────┘
             ↑ 贯穿三层：AI 辅助 + 插件可扩展 + 开源
```

**近期做身份一，架构上为身份二/三预留，价值上以身份三立命。**

### 2.3 目标用户

1. **个人**：译者 / 双语工作者（1 人），要高效翻译并积累自己的资产；
2. **小团队**：内部 2–10 人翻译组，共享 TM/术语、分工、审校；
3. **小型企业内部**：出海制造、跨境电商、律所、事务所、科研机构的双语员工或专职译员；
4. **（长期）生态开发者与被接入的系统**：想给本项目写过滤器/连接器/插件的人，或想把翻译能力嵌入自身流程、把成果沉淀到本中枢的外部系统。

### 2.4 设计取舍

1. **AI 原生、贯穿全流程、可关可溯**：翻译、审校、QA、资产养护处处有 AI，但每处产出标注来源、可整体关闭；
2. **资产中枢为脊梁**：一切设计围绕"成果能否沉淀、能否被养护、能否被复用"；
3. **核心精简 + 插件扩展**：核心只做通用能力，格式/引擎/处理步骤/连接器皆为可插拔；
4. **开放接入**：CLI、本地 API、文件夹监听、剪贴板、编辑器/浏览器插件、webhook——凡需沉淀处皆可接入；
5. **跨平台桌面**：Windows / macOS 一致（**不做 Linux 端**）；
6. **CJK 一等公民**：字符计数、CJK 分词模糊匹配、中英混排与标点、繁简转换、国产引擎内建；
7. **数据主权与可移植**：一切资产以开放标准随时导出；开源保证不被绑架。

### 2.5 非目标（需求评审硬门禁）

**A. 当前范围不包含**（不服务当前目标用户，默认不进需求）：
- ❌ 客户门户 / 对外交付平台；
- ❌ 报价、费率、报价单、发票、应收台账、任何计费；
- ❌ 供应商/译员采购、外包派单、抽成市场；
- ❌ 企业级数据隔离、复杂权限矩阵（RBAC）、操作审计日志、重型合规（认证/数据驻留/AI 内容标识）。

**B. 核心不内置，但插件系统为其预留扩展点**（技术边界，靠生态承载）：
- ⛊ 软件本地化资源格式（`.po`/`.resx`/`.strings`/`.arb`/`.properties`/开发者键值 JSON/YAML）——**通过格式过滤器插件扩展**；
- ⛊ Git/CMS/Figma 等连接器、持续本地化流水线——**通过连接器插件 + API/webhook 扩展**；
- ⛊ 特定垂直格式（CAD、字幕高级特性等）——**通过过滤器插件扩展**。

> A 与 B 的区别：**A 是当前产品范围上的"不做"，B 是架构上的"核心不做但为你留门"。** 不得混淆；接入与插件能力服务于翻译与资产沉淀，不借此扩展成对外交付/计费门户。

**C. 与 CAT 定位无关：**
- ❌ 口译/同传/语音实时翻译（语音**转写后**作为文档翻译对象可经插件接入，属 B）；
- ❌ 自建 MT 引擎训练（只做外部引擎接入 + 提示工程层自适应）。

## 3. 用户画像与关键场景

### 3.1 个人译者"老周"（起点场景 + 个人资产沉淀）

法律/机械中英译者，Windows + MacBook。要高效翻完手上文档，AI 帮忙但不添乱，**且十年功力沉淀成自己的 TM 与术语，越用越顺手**。
1. 60 页 PDF 合同拖入 → 文本层抽取（扫描页 OCR）→ 分段 + 字数分析；
2. 挂载自有法律 TM/术语，选引擎（本地模型或云端），接地预翻译 + QE 打分；
3. 编辑器逐段确认，术语提示、QA 实时报错、划词 AI 润色；
4. 导出保版式译文 + 双语对照；**确认内容自动回流 TM，AI 夜间养护去重纠错**；
5. 半年后，他的资产库已能覆盖新合同 40% 内容，且 AI 从历史语料替他挖出一份法律术语表。

### 3.2 内部翻译小组"小林"（协作 + 共享资产中枢）

5 人组做制造业出海文档。要共享一套 TM/术语、能分工审校看进度——但不要企业服务器、复杂权限、审计。
1. 建项目 → 按文件/段落分派，设交期；
2. 译员各自翻，实时共享同一中枢的 TM/术语（内网一容器）；
3. 看板看进度与 QA；审校带修订痕迹改，译员回改；
4. 领导过目走"三栏 Word 往返"；
5. 项目归档，成果沉淀为小组共享资产，**AI 定期出"术语漂移报告"提示不一致**。

### 3.3 小企业双语员工"Amy"（增量复用 + 低门槛 AI）

市场部，非职业译者。手册更新只翻变更部分（TM 复用 78%），新段落走接地 LLM + QE 路由，术语库锁定产品名/禁译品牌名，导出版式一致直接发布。

### 3.4 （长期）生态开发者"K"与被接入系统（通用 CAT + 接入）

- K 想让本项目支持一种小众 XML 文档 → 写一个**格式过滤器插件**，几十行声明抽取规则即可；
- 某内部 wiki 系统想让页面更新时自动送翻并把成果沉淀到中枢 → 调**本地 API / webhook**，翻译在本项目发生、TM 自动积累；
- 有人想接一个新上线的国产大模型 → 写一个**引擎连接器插件**，社区共享。

> 场景 3.4 点明长期形态：本项目不只是封闭的自用软件，更是可被生态围绕、可被任意流程接入的翻译与资产底座。

## 4. 架构支柱

这三根支柱是"通用 + 可接入 + 可扩展"能落地的前提，必须**从 M0 起就在架构中成立**，即便初期实现有限。

### 4.1 支柱一：过滤器 / 管线核心（Okapi 范式）

- **统一内部表示**：任何输入（docx/pdf/xliff/…未来的任意格式）经**格式过滤器**转换为统一的"文档对象 + 段落对"内部模型；一切下游能力（编辑器、TM、QA、导出）只面向这个统一模型，与具体格式解耦。
- **管线步骤（Pipeline Steps）**：分段、预翻译、QA、术语标注、伪翻译、格式转换等都是可链式组合的**步骤**；用户/插件可编排管线（如"导入 → 分段 → TM 预翻译 → LLM 接地补全 → QA → 导出"）。
- **收益**：新增一种格式 = 写一个过滤器，不动核心；新增一种处理 = 写一个步骤。这是"通用 CAT"与"插件生态"的架构地基。

### 4.2 支柱二：资产中枢（产品脊梁，详见 §7 D/E/J/AC 模块）

- TM、术语、双语/单语语料统一存储、统一检索、统一养护；
- **对内**为编辑器/预翻译/QA 供给；**对外**通过 API 接收任意来源的成果回流；
- **AI 养护层**（§7.AC）持续提升资产质量——这是中枢的"活性"来源。

### 4.3 支柱三：插件系统与开放接口（一等架构支柱，详见 §7 P/X 模块）

- **扩展点（首批规划）**：格式过滤器、MT/LLM 引擎连接器、QA 规则、管线步骤、AI 动作（划词菜单项）、导入导出器、编辑器 UI 面板、外部系统连接器；
- **接入方式**：本地 HTTP/gRPC API、CLI、文件夹监听、剪贴板、编辑器/浏览器插件、webhook 出入；
- **治理**：清晰的插件清单（manifest）、能力声明、权限边界（插件能访问什么资产/网络需显式声明）、版本兼容策略；官方维护"核心插件"，社区贡献"扩展插件"。

## 5. 产品原则

1. **资产至上**：任何翻译动作的默认归宿是"沉淀为可复用资产"；丢失或不养护资产视为严重缺陷。
2. **使用者主权**：AI 产出标注来源、可整体关闭；工具服务判断，不做不可见决定；用户语料零训练用途外泄。
3. **核心精简、边界靠插件**：核心只做通用且稳定的能力；一切易变/长尾/垂直的东西下沉到插件。新功能进核心前先问"这能不能是个插件"。
4. **开放优先**：数据用开放标准、能力有开放接口、扩展有开放插件；开源可审计、可自托管。
5. **本地优先（务实默认）**：核心功能离线可用；联网只为 AI 引擎与协作/接入同步。
6. **交付件保真**：导出版式忠实度是硬指标。
7. **范围克制**：§2.5-A 是当前范围门禁；计费/门户/供应商类能力默认不进需求，也不借插件之名变相做大。

## 6. 功能模块总览

优先级：**P0** = MVP 必备；**P1** = MVP 后约 6 个月；**P2** = 远期。
标签：`[核]`核心内置 · `[插]`以插件形态提供（核心留扩展点）· `[中]`资产中枢相关。

```
A 项目与文件管理        B 文档格式引擎[核+插]      C 翻译编辑器
D 翻译记忆(TM)[中]      E 术语库(TB)[中]           F MT/LLM 引擎集成[核+插]
G AI 辅助套件           H 质量保证(QA/LQA)         I 审校与内部协作
J 对齐与语料回收[中]    K 统计与分析               L 互操作与标准
AC 资产养护中枢[中]★    P 插件系统与扩展★          X 开放接入层★
M 数据与设置           N 平台·安装
```

★ = 架构支柱相关模块。当前范围**不包含**：报价/费率/发票、授权定价、企业级隔离/审计/重型合规、数据流审计面板、涉密模式。

#### B 专述：PDF（M0 纳入，实现方案后续专项讨论）

调研（附录 A-9）确认 PDF 是最高频也最难保真的场景，M0 即纳入，按难度分层、按"尽力保真 + 明确降级"管理预期：

- **文本层 PDF**（M0 必达）：抽取文本流 + 版面结构（段落/标题/表格/多栏阅读顺序）；采用"**转换 → 翻译 → 重建**"主路径（业界复杂文档标准做法），而非原地改字；导出**版式尽力还原的 docx**（首选）与/或回写 PDF；显式处理三大难点——① 真表格 vs 视觉伪表格识别；② 多栏阅读顺序校正；③ 中↔英文本膨胀/压缩导致的溢出。
- **扫描件/图片**（M0 起步）：内置 OCR（本地优先，云可选）→ 原文可编辑；提供**原图 vs OCR 文本对照校验 UI**。
- **期望管理**：承诺"尽力保真 + 降级清单"，非像素级还原；不可保真元素导出时附清单。
- **实现路径**（转换引擎/版面分析/OCR 选型）留待专项设计讨论；PRD 只锁定"M0 有 PDF、按此口径交付"。

**B 验收**：50 份真实文档样本（含 PDF）导出后人工版式检查通过率 ≥ 95%（PDF 按"尽力保真"单列）；导入失败必须给可理解错误，禁止静默丢内容；**过滤器 SDK 能让一名开发者在半天内为一种新简单格式写出可用过滤器**。

## 9. 版本规划

**总原则**：M0 用文档翻译这一首要场景**把核心 + 资产沉淀 + 插件化架构验证透**；通用化与生态在 M1/M2 沿既定架构展开——因为架构从 M0 起就为它们预留，扩展是"填空"而非"重构"。

### M0 —— MVP（一个人靠它完成真实文档翻译，且成果开始沉淀）

- **格式**：DOCX/XLSX/PPTX/TXT/MD/HTML/XLIFF + **PDF（文本层必达、扫描件 OCR 起步）**；SRX 分段；**格式以内部插件形态实现（验证过滤器架构）**；
- **编辑器**：双栏+预览+TM/术语/MT 面板+自动传播+实时机械 QA+CJK 输入；
- **资产**：本地 TM/TB + 标准互导 + CJK 模糊匹配 + **成果自动回流中枢（AC-02）**；
- **引擎**：≥6 家 + OpenAI 兼容端点 + **接地翻译管线** + 批量预翻译 + 划词 AI；
- **架构**：过滤器/管线核心成立；引擎以连接器形态实现（验证连接器架构）；
- **平台**：Windows / macOS 双平台（Electron 壳 + Rust 无头引擎核）；本地存储、崩溃恢复；开源仓库与基础构建文档。
- **M0 刻意不做**：第三方插件 SDK 开放、AI 深度养护、QE、协作、通用接入 API——但**架构均为其预留**。

### M1 —— 1.x（约 6 个月：AI 铺开 + 资产养护 + 插件 SDK 开放 + 通用化起步）

- **资产养护中枢**（AC 全套 P1）：AI 规则/语义清洗、质量分级、术语挖掘、漂移报告——**兑现"资产中枢"承诺**；
- **AI 铺开**：QE 路由、AI 语义 QA、AI 术语提取、Fuzzy Repair、会话内自适应、原文诊断、智能标签放置、AI 智能对齐；
- **插件 SDK 开放**：格式过滤器/引擎连接器/QA 规则/管线步骤/AI 动作/UI 面板扩展点 + 文档 + 示例；官方 IDML/SRT 作为插件落地；
- **通用接入起步**：本地 API + CLI（X-01/02）；
- **协作与互操作**：双语审校往返、项目包交接、对齐器、SDLXLIFF/MQXLIFF；
- 项目模板、版本更新流、LQA 精简评估。

### M2 —— 2.x（生态、通用性纵深、协作）

- 插件市场/索引与脚本接口；更多接入方式（文件夹监听、剪贴板、webhook、编辑器/浏览器插件、连接器示例）；
- 后台定时养护、语料导出训练集、养护策略插件；
- 内网轻量实时协作、朴素角色与任务指派、代理式批处理管线、多模态辅助、AI 风格学习；
- 更多官方过滤器插件（垂直格式）、片段召回、单语语料。

## 12. 开放问题（需决策）

1. **技术栈与跨平台方案**（已定）：UI 壳 **Electron**（不用 Tauri，因三 webview 的 CJK IME 一致性风险）；引擎核 **Rust 无头进程**；平台 **Windows + macOS 双平台，不做 Linux**。
2. **插件运行时形态**（基线已定，细节待设计）：三层模型——Tier 1 声明式清单（零代码，覆盖多数引擎与简单格式）/ Tier 2 沙箱 JS（UI 面板与 AI 动作）/ Tier 3 进程外协议插件（任意语言含 Python，崩溃隔离）；WASM 作为后续可选传输层，非 M1 承诺。待定：协议细节、权限粒度、脚本桥语言。
3. **开源许可证**：核心与插件是否同一许可（如核心 MPL/Apache + 插件宽松），贡献者协议；
4. **PDF 实现路径**：转换/版面分析/OCR 选型与扫描件保真深度（专项设计讨论）；
5. **资产中枢存储**：本地嵌入式库 vs 可选自托管服务端；聚合规模到千万级的存储/检索方案；
6. **QE/语义养护本地模型**（COMET/嵌入类）是否随包分发（体积 vs 开箱）；
7. **首发引擎名单与默认推荐**（国产 vs 国际，按实际可用性）；
8. **API/接入的鉴权模型**（本地优先场景下的最小安全边界）；
9. 是否需要移动端/网页端只读进度查看（P2 后议）；
10. 产品/项目命名与社区建设策略。
