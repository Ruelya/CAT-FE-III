# Translunar CAT development walkthrough: July 25-27, 2026

> **Historical record (pre-greenfield).** This walkthrough describes the
> previous implementation, which was removed in the greenfield reset.

This document explains what changed during the latest three development days,
what each group of tasks delivered, and what the work taught us. It is written
for readers who do not need to follow the Rust, TypeScript, Electron, or Trellis
implementation details.

## Where the project started on July 25

The product already had a substantial CAT core: projects and documents,
translation memory and terminology, multiple document formats, a professional
editor, AI provider integration, QA/review, analytics, asset curation, and a
first plugin foundation. The remaining work was concentrated in product
packaging, visual convergence, and the deeper public plugin ecosystem.

The team also corrected an important planning problem. Several old tasks were
written as MVP-sized approximations even though the governing requirement was
the complete product PRD. Those plans were expanded so that future completion
claims require real lifecycle behavior, persistence, permissions, recovery,
desktop flows, and evidence rather than a narrow demo path.

## July 25: turn the codebase into a shippable desktop product

The platform and product-shell work established the practical boundary around
the application:

- Windows and macOS packaging, build metadata, licenses, and release-facing
  documentation were added.
- Desktop localization and shell behavior were exercised as product features,
  not treated as build-only concerns.
- A crash-recovery scenario proved that an editor draft survives an Engine
  failure instead of silently disappearing.
- Trellis dispatch was hardened so that a spawned worker is considered ready
  only after a durable start event and a confirmed task delivery.

Two follow-up tasks were planned from issues found during this pass. One covered
Node 24 and Electron compatibility; the other covered the gap between the live
Workbench and its approved visual reference.

## July 26: modernize the toolchain, then repair the visual and plugin foundations

### Node 24 compatibility

The project moved to an Electron version that supports the current Node 24
development environment and declared the missing SDK test dependency. This
removed the local `extract-zip`/Electron install failure that had made Node 22
look like a permanent product constraint. Node 22 is no longer the reasoned
target; Node 24 is supported by the repository toolchain.

### Workbench visual identity

The Workbench received bundled typography, truthful loading and empty states,
global search, a clearer Suggestions hierarchy, denser segment actions, and a
real document-preview treatment. Design tokens, light/dark behavior, reduced
motion, and multiple viewport sizes were checked with screenshots.

This work improved consistency, but it did not fully reproduce the approved
visual anchor. The current interface uses the right warm palette, dark chrome,
five-color band, and technical typography, yet it is still substantially more
sparse and smaller in scale than the reference. That gap is documented below
rather than hidden behind a passed regression test.

### Plugin runtime foundations

Three foundations were completed:

- Tier 3 plugins gained a supervised process host with bounded protocol traffic,
  timeouts, cancellation, crash isolation, and restart behavior.
- The runtime gained a tier-aware lifecycle control plane so declarative,
  sandboxed, and process plugins follow the same installation and activation
  rules.
- Capability grants became explicit, scoped, auditable, and independently
  checked at registration and use time.

The practical result is that a plugin no longer receives ambient authority just
because it is installed. The Engine retains control over what it may register,
what it may execute, and what is recorded in durable history.

## July 27: complete the public plugin execution surface

### Tier 1 and Tier 2 hosts

Tier 1 declarative plugins were connected to real Engine behavior while keeping
their intentionally limited, data-only trust model. Tier 2 added bounded
QuickJS execution with explicit host calls and resource limits. Both were
qualified through normal install, grant, enable, disable, upgrade, rollback,
and uninstall flows.

### Public Engine connectors

Versioned connector contracts were added so plugins can supply external Engine
integrations through the public SDK instead of importing private Engine code.
The implementation includes lifecycle ownership, exact grants, compatibility,
failure containment, examples, desktop inventory, and real Engine smoke tests.

### Public QA rules and pipeline steps

The final plugin-runtime child adds the two remaining public extension types:

- QA plugins can evaluate bounded segment data and return validated findings.
  Findings participate in the normal QA run, issue reconciliation, waiver,
  report, export-gate, and history flows with immutable plugin provenance.
- Pipeline plugins can validate configuration, consume and produce declared
  artifact kinds, publish versioned checkpoints, respond to cancellation, and
  resume through public SDK handlers after a restart.

These contracts work across the declarative, sandbox, and supervised-process
tiers. Registration and every invocation are independently authorized. Upgrade,
rollback, revoke, disable, uninstall, timeout, crash, and stale-generation
results are handled without letting an old plugin generation write into current
state.

The Desktop now exposes the public descriptors, grants, compatibility, owner,
tier, version, state, bounded failures, QA provenance, and pipeline execution
history. The renderer displays Engine-owned state; it does not execute plugin
logic or decide pipeline outcomes.

## Lessons from the three days

### A passing local test is not the same as a finished product path

The most valuable checks exercised install, consent, execution, persistence,
restart, upgrade, rollback, revoke, disable, and uninstall as one real Engine
flow. Unit tests remain necessary, but lifecycle bugs tend to live between
layers.

### Public contracts need separate version axes

A plugin descriptor version, operation protocol version, contribution version,
configuration schema version, and checkpoint schema version answer different
compatibility questions. Treating them as one number would make safe upgrades
and historical interpretation impossible.

### Cancellation and stale results are persistence concerns

Sending a cancellation signal is only half the solution. The Engine must check
cancellation and the active plugin generation again before writing output,
findings, checkpoints, or history. Otherwise a late response can overwrite newer
state.

### Provenance is part of user trust

QA findings and pipeline outcomes must remain explainable after a plugin is
disabled, upgraded, rolled back, or removed. Immutable version ownership and
bounded failure records make that possible without storing source text, secrets,
stderr, or raw plugin payloads in audit logs.

### Screenshot assertions and design fidelity are different gates

Overflow and overlap assertions can prove that a page is technically intact.
They cannot prove hierarchy, density, brand expression, or resemblance to the
approved design. Both automated geometry checks and direct visual comparison are
required.

### Large cross-layer tasks need an explicit final completeness pass

The QA/pipeline work initially proved retention of completed checkpoints but not
publication of a checkpoint during an in-flight operation followed by restart
and public `resume` dispatch. Reading the acceptance criteria literally exposed
that gap and led to the final transport and restart test rather than an MVP claim.
