### 仍未做到 Trados 同水准的部分（诚实清单）

这些**没有**假装完成，下一轮应继续：

1. **IME 与补全在富文本上的手感**——QuickPlace / ghost 已按 Trados 开口→闭口模型，但补全弹层仍锚在编辑器下方，避免和 IME 抢位。
2. **Word COM / 真 PDF 所见即所得**。现在是标签重建的 HTML 预览，不是原文件排版引擎。
3. **Approved / Rejected 七档**——引擎工作流是 translation/review/signed 三档，Signed = 锁定。
4. **AI 需真实 provider 密钥**才能生成；门禁验证的是“挂在当前段 + 无配置时诚实”，不是云端生成质量。
5. **PDF** 尚未纳入 format-matrix 的同构往返（引擎已注册 `builtin.pdf`）。
6. **QuickPlace 选中项高亮源跨度**——官方：列表当前项会在源段高亮对应格式文本。本轮列表已有格式样本，源列尚未联动高亮。
7. **复制/粘贴标签**——官方允许单独拷贝标签或连文本一起粘。当前粘贴仍是纯文本。
8. **标签保护开关**——官方 Protect Tags 默认关；本轮未做“禁止删除标签”。

主参照：SDL Trados Studio 2024 / 2024 SR1 的 Editor view（以 docs.rws.com 官方
文档为准）；补遗参照 memoQ（docs.memoq.com）与 CafeTran。协作、派单、云协同、
GroupShare / Trados Team 整段排除；本文只评**一个译者独立把一单活做完**。

所有"本项目现状"结论均来自 2026-08-15 对当前构建的实测（四轮脚本化真人剧本，

空壳 = 界面或接口存在，但能力不存在或与相邻能力不咬合。

## 1. 诊断

### 1.1 实测剧本与断点：一单活在哪里断

剧本：一份 10 段的真实感 DOCX（一处粗体、一处斜体、数字/日期/邮箱、两对重复
句）→ 建项目 → 导入 → 逐段翻译确认 → 处理标签 → QA → 导出。这是任何 CAT
工具的最小一单。**结论：这单活交不出去。**

| # | 剧本步骤 | 发生了什么 | 断点定级 |
| --- | --- | --- | --- |
| 1 | 打开/导入 DOCX | 10 段正确入网格，重复句保留 | 通 |
| 2 | 进入段网格 | 网格只有 #/源/目标/状态四列。源文里**看不到任何内联标签**——粗体词与普通文字渲染完全相同，译者不知道这段有格式 | 断（隐性） |
| 3 | 看 TM / 术语窗是否随段刷新 | 右侧唯一的情报窗"Exact TM"确实随当前段刷新；**术语窗不存在**（termbase 全在 Assets 页） | 半断 |
| 4 | 翻译、确认，看是否写 TM | Ctrl+Enter 确认成功，**确认确实写入 TM**（重复句立刻出现 exact 命中）。但确认后不自动跳下一未确认段 | 通（有毛刺） |
| 5 | 重复句能否吃到刚才的劳动 | TM 窗显示了 exact 命中，**但没有任何"应用"按钮**——译者只能盯着正确答案重新打一遍字 | 断 |
| 6 | 确认重复段 | **确认失败**。单人操作弹出 "segment was modified by another writer (conflict)" + save error；重试轮仍失败，10 段最多确认 8 段。根因：引擎在确认时同步自动传播到重复段（能力是真的），前端的修订快照没有跟上，把产品自己的传播当成了"另一个写入者" | **死断** |
| 7 | 打几个字看有无 AutoSuggest | 无任何建议 UI。Prefs 面板有 Autocomplete 开关、领域模型有 `autocomplete: bool`（默认 true）、契约有字段——**全仓没有任何代码消费它** | 断（空壳标本） |
| 8 | 放置标签 | Tags 面板列出源标签与 tag_missing 报错，放置交互是**数字偏移输入框 + Apply tags 按钮**；对全部 10 段逐一点击 Apply tags 后，QA 的 tag_missing **一个都没消掉**（10 处依旧） | **死断** |
| 9 | Concordance 查半句 | 编辑器内无任何入口。模糊检索与 Concordance 引擎能力存在，但长在 Assets 页——查一次要离开编辑器、手动粘贴 | 断 |
| 10 | 过滤出 Draft / 有批注 / 有 QA 错误的段 | 网格没有 Display Filter。Find 面板存在（Target/Source/Both + Case/Word/Regex），但点 Find **无计数、无跳转、无高亮**，用户按下去没有任何可感知反应 | 断 |
| 11 | 预览 | 不存在，任何格式 | 断 |
| 12 | 导出 | tag_missing 是 error 级、QA 门禁挡死；协议里有 `qa.issue.waive`，**UI 没有豁免入口**。导出永久 blocked | **死断** |

三个死断叠加的含义：**只要 DOCX 里有一个粗体词，这个产品就无法合规交付**。
目前唯一能从头走到尾的格式是纯 .txt——这正是 CI 里那条一直全绿的 E2E 路径，
也是"测试全绿"与"用户觉得几乎不能用"并存的原因。

亮点也要如实记录：QA 面板的规则是真的（空目标/标签/数字不匹配/长度比），
**每条 issue 带 Jump 跳回段**；确认写 TM 是真的；Undo/Redo/History（操作日志）、
Split/Merge、改源文（带 reason）、简繁转换、拼写面板都存在。零件的成色并不差，
差在没有一条围绕当前段的完整链。

### 1.3 三个结构性病灶（比单个缺口更重要）

1. **情报与动作分离。** 引擎能力大量真实存在（fuzzy 检索、concordance、术语
   CRUD、豁免、传播、QE），但被安置在"资产/管理"型页面里，而译者的手在网格
   上。Trados 的每个情报窗都以当前段为查询键、以目标光标为落点；本项目的对应
   能力以"库"为查询键、以"管理列表"为落点。这就是 PRD 把"中枢"当脊梁的直接
   代价——**能力都有家，但都不在工作发生的地方**。
2. **只读展示，不可执行。** Exact TM 命中不能 Apply；QA 报 tag_missing 但标签
   不能放；协议有 waive 但界面不能豁免。界面把"知道"给了用户，把"做"留给了
   用户手工重打。专业工具的价值恰恰在"知道→一键做"。
3. **后台智能与前台状态失联。** 引擎确认时自动传播（好设计），但 UI 的修订
   快照跟不上，把自家传播当成"另一个写入者"，让重复段永远无法确认。这类
   "引擎单干、前端不知情"的失联，是"接口在而能力不咬合"的机制性来源。

### 1.4 与现行 PRD 的修正关系

现行 PRD（docs/PRD.md v2.0）的一句话立意以"沉淀中枢"为纲：起点/终点/中枢三
角里，"编辑器"甚至没有作为名词出现。修正如下，**下一轮开发以本节为准**：

> **修正立意**：做一个开源的通用 CAT——专业翻译工作发生在**段级编辑器**里；
> TM、术语、QA、AI、语料是**围绕当前段**的工作台能力；资产中枢是编辑器工作
> 的**自然沉淀与背后管理面**，不是与编辑器并列的产品形态，更不是产品脊梁。
> 评价一个功能是否纳入的标准修正为：**它能否挂在当前段上，让一个译者把一单
> 活做得更快、更准、更省心；不能挂在当前段上的能力，必须证明自己是编辑器
> 背后的必要沉淀或必要进出口，否则后置。**

对 PRD 结构的具体修正映射：

| PRD 现状 | 修正 |
| --- | --- |
| "沉淀中枢"作为三角之一且实际主导任务拆分（历史任务 14/31 个围绕资产/互操作/管线/插件） | 中枢降为"编辑器后端"：TM/术语库的价值以"编辑器内命中率与插入次数"度量，不以"库管理页功能数"度量 |
| 编辑器散落在 B 类（文件处理）与 C 类（编辑体验）需求点里，无独立骨架章节 | 新增"编辑器工作台"作为第一公民章节，内容即本文件 §4 的原子分解 |
| AI 章节（F/G 类）以 provider/批处理/对话为主体 | AI 需求重排：**段内建议/改写/接受/驳回/术语约束**为 P1，批处理为其派生；侧栏聊天不作为 AI 原生的达标形态 |
| 互操作（SDLPPX/XLIFF 包）作为近期主线 | 后置。编辑器骨架未立时，多一种进不了编辑器闭环的格式只是多一个孤岛入口 |
| 协作(I 类) | 本轮整段排除（用户指令）；唯一保留物是把 collab.lock 原语借给单机"段锁定" |
| 验收惯例：功能可达、E2E 全绿 | 修正为：**真实文件进、正确文件出**。每条链的验收剧本必须包含一个带格式的真实 DOCX 与一个真实 TMX（见 §5.3） |

## 2. 四角色交叉视角与冲突

**从业译者/审校**（以 Trados 日用路径为准）：最痛的不是缺功能名，是缺"手感
闭环"——确认必须跳下一段；命中必须能一键入目标；术语必须自动跳出来；QA 必须
在我确认时就告诉我，而不是导出前给我 29 条清单。对他们而言 §1.1 的三个死断
等于"这不是工具，是展示品"。他们不关心 240 个 RPC 方法。

**软件开发**：好消息是绝大多数缺口是"前端把已有引擎能力挂到当前段"而非新造
引擎（fuzzy=tm.search、concordance、term.search/upsert、waive、propagated 都
在）；坏消息是 Workbench 的状态层（save-coordinator/修订快照/全量刷新）已经
在传播竞态上露了怯，往上叠 TM 应用、术语插入、AI 建议前**必须先把"段状态的
单一事实源"理顺**，否则每加一个写入者就多一类 conflict。

**架构师**：冲突点一：情报窗体系要不要做成通用 dock 框架？结论：不要。v1 用
固定布局的右侧窗栈（TM/术语/QA/批注四窗常驻可折叠），把"可拖可浮"让给未来；
过早做停靠框架是又一次"骨架先行、能力空心"。冲突点二：AutoSuggest 的候选源
要不要进引擎？结论：要——候选合并、排序、去重、大小写策略放引擎（新方法族
`editor.suggest`），渲染进程只管 UI；否则 IME 环境下的性能与一致性都保不住。
冲突点三：标签模型。DOCX 过滤器把每个 run 当保护标签是保守正确的**存储**
决策，但把它原样暴露为**用户义务**是错误的呈现决策；需要引入"格式标签
（可见、可放置）vs 结构噪音（自动结转）"的分层，宁可引擎在导出时自动结转
单 run 段的标签，也不能让每段都背 tag_missing。
（若未来引入 Okapi 作过滤器基础设施，此分层同样是对接面；本轮不做。）

**项目经理**：冲突点是范围诱惑。上一轮"前端成品化"的教训是打磨了 136 张截图
的壳，却没让一单活走通；这一轮最大的风险是把 §4 的 40 个原子又全都想要。
本文用"死断优先"排序：先让 §1.1 的三个死断消失（W 组 + R6/R4），此时产品
从"不能用"变"能用"；再做 TM/术语/补全（此时从"能用"变"好用"）；AI 段内化
放第三（从"好用"变"领先"）。每个里程碑都以真实剧本收口，而不是以功能数收口。

**四方共识**：修 bug 也是做功能——W1（传播竞态）既是译者的死断、开发的技术债、
架构的单一事实源问题，也是 PM 的最小可交付物。

## 3. 原子任务分解

约定：
- 每个原子标注**挂载点**（网格本身 / TM 窗 / 术语窗 / 补全层 / 过滤审校 /
  预览 QA / 段内 AI / 编辑器后端），禁止"编辑器模块"式口号。
- **用户侧**：谁、在一单的哪一步、为什么、交互（含键盘）、成功标准。
- **技术侧**：依赖、如何挂在当前段、架构约束。
- 编号前缀即优先级分组（W=骨架 P0，L=段生命周期 P1，T=TM/术语/补全 P2，
  R=过滤审校预览 P3，A=段内 AI P4，S=资产沉淀后端 P5）。组内大致按依赖排序。
- 引擎方法名指既有协议方法；标 ★ 的表示需要新增/修改引擎接口。

### W 组 · 工作台骨架（P0：不消灭死断，后面全是零件）

**W1 传播竞态修复：单人永远不再看见"another writer"**
- 挂载点：网格本身（段状态事实源）。
- 用户侧：译者，步 6（确认重复段）。现状是重复段永远确认不了。成功标准：
  10 段含两对重复句的剧本，10/10 可确认，全程零 conflict 横幅；传播发生时
  当前编辑不被打断。
- 技术侧：confirm 返回的 `propagated` 必须进入行缓存并更新对应行的
  revision 快照（save-coordinator 与 use-app-controller 的行合并路径）；
  凡引擎侧产生的行变更（传播/批量操作/AI 应用）统一走同一条"行合并 + 快照
  重定"通道。约束：不允许再出现"全量刷新绕过活动编辑快照"的第二条路径。
  这是后续一切多写入者功能（T2/T8/A1）的地基。

**W2 传播的可见化：origin 与回链**
- 挂载点：网格本身 + TM 窗。
- 用户侧：译者，步 6。被传播的段要能一眼认出（"来自 #4"徽标），点击跳回
  原段；传播段默认 draft，需人工确认。成功标准：重复句确认后，其孪生段
  出现传播徽标与回链，Display Filter（R1）可按"传播"捞出。
- 技术侧：引擎 confirm 结果已含 propagated；★ 需在 segment 元数据中落
  `origin`（human / propagated:{segmentId} / tm:{score} / mt / ai:{runId}），
  这是 C 组匹配率列、A 组 AI 溯源共用的字段，一次定义。

**W3 内联标签可见化：网格里画出标签胶囊**
- 挂载点：网格本身。
- 用户侧：译者，步 2。源文里的 `<1>…</1>` 以紧凑胶囊渲染（编号+悬停详情），
  目标编辑器内已放置的标签同样可见。成功标准：带粗体的段，译者不看 Tags
  面板即知格式跨度在哪；标签在 IME 输入中不可被光标拆碎。
- 技术侧：sourceTags/targetTags 数据已随行返回；TargetEditor 从纯 textarea
  升级为受控富文本（contenteditable + 受保护 inline atom）。**这是本轮最大
  的单体前端工程**，是 T7（QuickPlace）与 D 类一切能力的载体，必须先行。
  约束：IME 组合事件（现有 isComposing 逻辑）必须保持；性能预算沿用现有
  按键延迟中位数 <5ms。

**W4 情报窗栈：右侧固定四窗（TM / 术语 / QA / 批注）随当前段刷新**
- 挂载点：TM 窗 / 术语窗 / 过滤审校（容器）。
- 用户侧：译者，步 3-9 全程。四窗常驻可折叠，全部以当前段为查询键；
  F6 在网格与窗栈间跳焦点，窗内条目可上下键选择。成功标准：换段 ≤200ms
  内四窗内容一致指向新段；键盘可从网格进窗选中第一条命中并返回。
- 技术侧：现 TmExactPanel 泛化为 DockStack（仍是固定布局，不做拖拽停靠）；
  每窗一个以 (documentId, segmentId) 为键的查询 hook，统一取消竞态（换段
  时旧请求作废）。约束：窗内容加载不得阻塞网格输入。

**W5 匹配率 / origin / 结构三列进网格**
- 挂载点：网格本身。
- 用户侧：译者/审校，全程。每行显示：译文来源徽标（W2 的 origin）、
  匹配分（若来自 TM/MT）、文档结构缩写（标题/正文/脚注，悬停全路径）。
  成功标准：一屏内分辨"哪些段是机器给的、哪些段在文档的什么位置"。
- 技术侧：structural_path 引擎已存（document.xml#p:N），映射为短标签；
  列可在 Prefs 里显隐。依赖 W2 的 origin 字段。

**W6 状态栏：文件 · 段号 · 确认统计 · 生效过滤器**
- 挂载点：网格本身（底部条）。
- 用户侧：译者，收尾步。常驻显示"当前 #N/总数 · 已确认 X · 草稿 Y · 
  过滤器：Draft"，点击统计即打开 R1 过滤器。成功标准：任何时刻不滚动
  即知进度与位置。
- 技术侧：counts 已有；补当前段序号与过滤器状态。纯前端。

### L 组 · 段生命周期（P1：让确认这只手不离键盘）

**L1 确认三走法 + 自动跳段**
- 挂载点：网格本身。
- 用户侧：译者，每一段。Ctrl+Enter=确认并跳下一**未确认**段（默认）；
  Ctrl+Alt+Enter=确认跳下一段；Ctrl+Shift+Enter=确认停留。成功标准：
  连续翻译 10 段手不碰鼠标。
- 技术侧：确认成功后的焦点推进逻辑挂在 W1 修好的行合并通道上；
  跳段目标 = 传播产生的 draft 也算"未确认"。纯前端 + 现有 confirm。

**L2 状态模型对齐：至少 5 档 + 段号列右键菜单**
- 挂载点：网格本身。
- 用户侧：审校，复核步。右键段号列：改状态（Draft/Translated/Approved/
  Rejected）、复制源文、清空目标、锁定（L3）、Add as New（L5）；支持
  Ctrl+点选多行批量。成功标准：审校可以不碰目标文本完成一轮判定。
- 技术侧：协议已有 segment.workflow.set（**目前 UI 未接**）；★ 状态枚举需
  与引擎对齐扩展（rejected/approved）；QA 门禁与导出语义随状态更新。

**L3 段锁定（单机版）**
- 挂载点：网格本身 + 过滤审校。
- 用户侧：译者，接稿步（客户锁定了不许改的段）与自查步。锁定段灰显不可
  编，QA 默认跳过，过滤器可按锁定捞。成功标准：锁定段无法被任何编辑动作
  （含传播、批量、AI 应用）修改。
- 技术侧：★ segment 增加 locked 位（单机语义，不复用 collab.lock 的租约
  模型，但预留同一字段名以便未来合并）；引擎在 updateTarget/confirm/
  propagate/tag.set 全部写路径上强制拒绝。**引擎强制，不是 UI 禁用**。

**L4 Copy Source / Clear Target / Clear all Drafts**
- 挂载点：网格本身（命令栏 + 右键）。
- 用户侧：译者。Ctrl+Ins=当前段复制源文；批量版只填空目标。成功标准：
  数字/代号密集段一键起稿。

## 4. 优先级与执行顺序

```
里程碑 M1 「能用」：W1 → R6 → W3 → L1 → R4 → W4
  出口剧本：§1.1 的 DOCX 剧本 12 步全通，导出文件解包验证格式正确。
  （W1/R6 消死断；W3 是标签与补全的载体；L1 是手感底线；R4 解导出死锁）

里程碑 M2 「好用」：T1 → T4 → T5 → L2 → R1 → R3 → T7 → L7 → W5/W6 → T3
  出口剧本：同一稿件二次翻译，TM/术语命中零重打；审校用过滤器捞段完成
  一轮状态判定；QA 在确认时点亮。

里程碑 M3 「快用」：T6 → T2 → T8 → L4/L6 → R2 → S1
  出口剧本：预翻译起稿 + 补全，实测键击数相对 M2 下降（记录基线）。

里程碑 M4 「领先」：A1 → A2 → A4 → A3 → R5 → L3/L5 → S2
  出口剧本：AI 候选在段内生成/应用/驳回全程可溯源，QE 分导引审校。

持续：S3（真实语料）从 M1 第一天起生效——没有真实文件的剧本不算过。
```

### 创新的分类与取舍

可行创新（挂当前段、单人一单用得完、与现有引擎咬合）：
- **确认即沉淀的可见化**（S1）：把"攒资产"变成即时反馈，这是本产品相对
  Trados 的叙事差异点，成本极低。
- **origin 全链路**（W2）：Trados 的 origin 只到 TM/MT；本项目把传播/AI/
  人工改动统一进一个溯源模型（A3），审校与复盘价值更高。
- **QE 导引审校**（A4）：引擎已有离线 QE，竞品多为付费云能力。

没有编辑器落点的批处理花样。判据始终是：**它挂在当前段的哪一侧？**
