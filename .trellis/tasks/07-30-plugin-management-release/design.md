# Technical Design: Plugin Management and Release Qualification

## 1. Boundary and Data Flow

```text
local directory / .tlplugin file          packaged app resources/plugins
              |                                      |
              v                                      v
      source materializer                    trusted root + index loader
              |                                      |
              +-----------> staged directory <-------+
                              |
                    normalize + validate + hash
                              |
               Engine lifecycle/version transaction
                              |
           permission review -> host preflight -> exact attach
                              |
           generated RPC projections -> desktop management UI
```

Archive extraction, bundle discovery, source classification, package hashing,
version selection, authorization, and activation stay in Rust. Electron main
only selects a local file/directory and supplies the configured packaged-resource
root when starting the Engine. React renders generated projections and sends
revision-safe commands.

## 2. Local Package Materialization

Introduce one plugin-runtime source materializer used by inspect, install, and
upgrade:

```rust
enum PluginPackageSourceKind {
    LocalDirectory,
    LocalArchive,
    Bundled,
}

struct MaterializedPluginPackage {
    root: PathBuf,
    cleanup: Option<TempDir>,
    source_kind: PluginPackageSourceKind,
    normalized_manifest: NormalizedPluginManifest,
    package_hash: PluginPackageHash,
}
```

Directories keep the existing secure copy path. `.tlplugin` is ZIP with a
single package root and a required format marker/index version generated by the
repository packager. Extraction validates normalized entry names before any
write and writes only beneath a fresh staging directory using create-new
semantics. The existing tree hash remains canonical so container metadata never
changes package identity.

Use the existing package limits as uncompressed limits and add a smaller fixed
archive-byte limit plus compression-ratio guard. Reject links from ZIP mode
bits, encrypted entries, data-descriptor ambiguity not supported by the chosen
reader, duplicate/case-folded names, unknown compression, and non-file/
non-directory entries. Validate the fully extracted tree again with existing
link/reparse/path/hash logic.

## 3. Distribution Metadata

Extend the normalized public manifest with optional closed distribution metadata
for compatibility:

```text
distribution.publisher   bounded display name
distribution.license     bounded SPDX-style expression
distribution.homepage    optional normalized https URL
```

Legacy packages project `distribution = null`. The release packager requires
metadata and a root `LICENSE`/`LICENSE.*` for every allowlisted core package.
Runtime source kind is not a manifest field.

Add durable source kind and distribution metadata to plugin installation and
immutable version projections with additive migration 24. Version rows own the
historical provenance; the installation row mirrors the active version for fast
list/get. Migration maps existing installations to `localDirectory` and retains
all existing version/hash data.

## 4. Bundled Core Catalog

The build script reads a checked-in allowlist, builds each package, validates it,
creates deterministic `.tlplugin` archives, and emits a closed index containing
catalog version, package ID/version, relative archive name, canonical package
hash, archive hash, tier, publisher/license, and contribution summary. It never
discovers arbitrary directories implicitly.

Electron packaging copies only the generated catalog directory. Desktop starts
the Engine with an explicit `--bundled-plugin-root <resources/plugins>` option.
The Engine canonicalizes the root once, loads the bounded index without following
links, verifies archive hashes before inspection, and keeps safe catalog
diagnostics separate from installed-plugin health.

Add generated protocol methods:

```text
plugin.bundled.list   PluginBundledListParams  -> PluginBundledPage
plugin.bundled.apply  PluginBundledApplyParams -> PluginLifecycleResult
```

`apply` resolves only an index ID inside the configured root. For an uninstalled
package it uses normal install; for a newer matching package it uses normal
upgrade with required expected revision; equal version/hash is idempotent.
Downgrade is never implicit. A newer app catalog does not auto-activate anything.

## 5. Engine Lifecycle Integration

Refactor existing inspect/install/upgrade entry points around the shared
materializer. Before committing a version:

1. Materialize into a fresh staging root.
2. Parse/normalize manifest and validate compatibility.
3. Compute canonical package hash and compare any catalog expectation.
4. Secure-copy into a new immutable managed-version directory.
5. Re-hash the managed tree before the Store transaction.
6. Create capability requests and candidate version state.
7. Preflight configuration, hosts, and every registry collision.
8. Atomically switch version/revision only after candidate attach is ready.
9. Compensate the exact candidate on any failure.

Restart and rollback verify the managed package hash before host construction.
Hash mismatch degrades only that plugin, detaches its exact generation, persists
a bounded diagnostic, and keeps ordinary Engine/built-in/other plugin calls
healthy.

## 6. Desktop Management Model

Keep one full-width operational Plugins surface with two unframed bands:

- Bundled catalog: compact rows for package identity, tier, license, bundled
  version, installed state, and install/update/restore action.
- Installed plugins: existing rows augmented with source badge, package/version
  state, full contribution inventory, diagnostics, and version actions.

Local install/upgrade uses the native picker (`openDirectory` plus `.tlplugin`
file filter), calls `plugin.inspect`, and opens an inspection dialog before any
mutation. The permission dialog remains the only grant authority. A version
history dialog loads `plugin.version.list` and submits `plugin.rollback` with the
current installation revision. Mutation success refreshes plugin, bundled,
provider, contribution, permission, and panel-session state together.

Split data/command helpers and focused subcomponents out of `PluginsPanel.tsx`
when needed to keep the existing component from accumulating another monolithic
state machine. Use generated contract types only.

## 7. Examples and Release Inputs

The allowlist includes only deterministic, production-safe public-SDK examples.
Fixture-only packages, fixed credentials, loopback test servers, and private
test adapters remain build/test inputs but are excluded from application
resources. All released examples get explicit license metadata and license text.

The package builder has check mode for drift and produces an evidence manifest
with archive/package hashes. Generated archives are either reproducibly built in
packaging jobs or checked only through deterministic hash fixtures; do not commit
opaque artifacts unless existing repository release policy requires it.

## 8. Failure and Security Model

- Archive/index/path failures map to the existing closed plugin package error
  family, with additive codes only where callers must distinguish integrity,
  format, or catalog unavailability.
- Safe diagnostics contain bounded IDs, phases, and codes, never absolute paths,
  archive entry payloads, environment, credentials, source/target text, stderr,
  or stack traces.
- Bundled root authority exists only in Engine startup configuration. Renderer
  sends catalog IDs, not resource paths.
- Install/upgrade/rollback remain optimistic-revision operations. Stale UI state
  reloads projections and cannot overwrite a concurrent lifecycle mutation.

## 9. Compatibility and Rollback

- Existing directories, manifest v1/v2 packages, SQLite rows, SDK callers, and
  lifecycle RPCs remain valid.
- Migration 24 is additive; old rows project as local-directory source with
  missing distribution metadata.
- The entire feature is removable by disabling the bundled root and continuing
  directory installation. Archive support does not change canonical identity.
- A failed release packager or catalog never alters installed plugin state.

## 10. Validation Strategy

Use pure runtime tests for adversarial ZIP parsing and canonical hashes, Store
migration/CAS tests for provenance, Engine tests for catalog/lifecycle/
compensation, script tests for reproducibility and allowlist policy, focused
React tests for state transitions, real Engine smoke for the complete lifecycle,
and Electron E2E plus screenshots for the user workflow.
